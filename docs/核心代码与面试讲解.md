# 核心代码与面试讲解

## 先用一分钟说清楚

“我做了一个英文客服意图分类和分流项目。它把问题转换成固定384维句子向量，再用自己训练的PyTorch分类头识别77类意图。我比较了TF-IDF逻辑回归基线，分开处理模型选择、概率校准和最终测试，并保留了转人工通道。编码器被冻结，实际训练的是小型分类头。项目由AI辅助实现，我能够解释和复现其中的训练与评估流程。”

最后一句中的能力应在完成教程、实际修改代码后再使用。

## 代码阅读顺序

1. `lesson_torch.py`：只学张量和反向传播。
2. `model.py`：完整但较短的分类头与训练循环。
3. `encoder.py`：文本如何变成向量，mask为何重要。
4. `data.py`：为什么数据划分决定结果是否可信。
5. `metrics.py`：概率、分流和统计区间。
6. `run_experiment.py`：把各模块按正确顺序串起来。
7. `predict.py`、`serve.py`：把模型变成可复用的接口。

## 逐模块说明

### `IntentHead.forward`

输入是 `[B,384]`，输出是 `[B,77]`。选中的结构为：

```python
nn.Linear(384, 128)
nn.ReLU()
nn.Dropout(0.15)
nn.Linear(128, 77)
```

可训练参数量59,213。最后一层不加softmax，因为训练使用`cross_entropy`。推理阶段才在`metrics.probabilities`中进行温度缩放和softmax。

### `train_head`

每个epoch进行训练，然后在selection集计算Macro F1。若本轮更好，复制权重到CPU保存；连续8轮未改善就停止，并恢复最佳权重。

这里`clone()`很重要：只保存引用会让所谓“最佳权重”继续跟着后续优化变化。训练时`model.train()`启用Dropout，评估时`model.eval()`关闭它。`inference_mode`避免评估阶段记录计算图。

### `FrozenEncoder.encode`

AutoTokenizer生成`input_ids`和`attention_mask`。AutoModel输出`[B,L,384]`的token向量。只对mask=1的位置求平均，再做L2归一化，得到`[B,384]`。

模型从固定版本的本地safetensors加载，不执行远程自定义模型代码；`requires_grad_(False)`冻结参数。训练头和推理使用相同池化、归一化和最大token数，避免训练推理不一致。

### `clean_training` 与 `prepare_data`

前者对文本分组，去掉空文本、测试精确重叠、标签冲突，并压缩同标签重复。后者分层划分并断言不同分区的规范化文本没有交集。审计记录同时保留移除数、分区大小和行ID签名。

去重只是规范化字符串匹配，不是语义去重。为保留官方测试，测试输入用于去污染，但测试标签不参与清洗或选择；这是公开说明的协议选择。

### `fit_temperature`

在calibration logits上寻找一个正数T，使正确类别平均负对数概率最小。搜索限制在预定范围0.25–4。如果搜索得到的温度比T=1更差，就保留1。这个过程不改变模型权重，也不改变Top-1类别。

### `select_threshold`

按小到大遍历预定阈值，选择第一个在calibration上满足经验准确率≥95%、接收数≥50的阈值。较小阈值接收更多或相同的样本，所以这对应候选阈值中的最大覆盖率。没有满足的阈值就设为1.000001，全部转人工。

“95%”是校准集上的经验目标。测试95.56%的Wilson95%区间约94.74%–96.26%，不能说保证线上≥95%。阈值搜索带来的选择偏差也不能靠同一校准集上的区间消除。

### `run_experiment`

固定计划 → 数据审计 → 特征提取 → 基线和神经结构选择 → 三种子训练 → calibration拟合温度和阈值 → 保存锁定文件 → 才计算test logits与指标。编码测试文本只是使用冻结编码器，不用标签拟合任何东西；测试分类结果在决定锁定后才计算。

### `IntentService`

启动时加载一次编码器和分类头。每个请求只做分词、编码、头计算、温度缩放与排序。用`weights_only=True`读取自己保存的分类头，检查编码器来源配置与checkpoint一致。

空输入和超过2,000字符的输入报错；没有英文字母的输入直接转人工。这不是完整语言检测或未知意图识别。一个领域外英文问题也可能得到高置信度误判，因此不能把低置信度转人工包装成经过验证的OOD检测。

可演示的实际局限：`I need help with my account.`被以约91.5%置信度判为`terminate_account`，即使它没有提出关户意图。这个合成例子没有加入测试指标，也没有据此重新选择阈值；它说明闭集分类器对模糊请求可能过度自信。

### `serve.py`

Python标准库HTTP服务只绑定127.0.0.1。输入是JSON，输出是JSON。网页用`fetch`调用`/predict`，把结果填进界面。真实人工平台没有接入，`human`只是返回的路由建议。推理锁让同一模型串行处理请求，性能报告也明确是并发1。

## 面试常见问题

**为什么选冻结编码器？**

五天入门任务里，冻结编码器允许缓存特征，训练快、显存需求低，更容易将注意力放在数据与统计评估上。代价是编码器不能适应当前意图区分；如果下一步做端到端微调，需要新计划和独立评估。

**为什么还要传统基线？**

文本任务里关键词已经很有用。只有和合理基线比较，才能知道更复杂模型是否值得。在本次同一协议下，传统基线87.47%，神经模型三种子平均91.90%。提升是4.44个百分点，不是44.4%。

**为什么选Macro F1，不只看Accuracy？**

它给每个类别同样权重，便于发现少数或困难意图的失败。本项目测试每类40条，仍同时报告Accuracy、Macro F1、Top-3和逐意图指标。不要只挑最有利的一项。

**部署种子42是不是挑出来的？**

不是。它在`experiment_plan.json`里预定，模型结构和阈值也在test评估前锁定。三种子平均用于展示随机性，而非挑最高测试分。

**相对改进和百分点有什么区别？**

从87.47%到91.90%，提升约4.44个百分点；相对准确率提升约5.07%。简历优先写百分点，最不容易产生歧义。固定部署seed42的差为4.48个百分点，不能和三种子平均的差混用。

**为什么校准后Accuracy没有变？**

正温度只缩放logits，不改变排序。校准改善的是概率质量与阈值解释，不是直接修正错分标签。

**95.56%的自动部分准确率是不是牺牲了全部覆盖？**

是一个取舍，必须同时报告覆盖率92.24%。人工作为未自动处理的剩余7.76%；不能只报95.56%而隐去转人工比例。

**bootstrap区间说明一定优于基线吗？**

它描述给定训练模型、当前测试样本下的准确率差不确定性。区间没有覆盖全部训练、预训练和未来领域变化，测试内也有少量重复。不能推断线上因果收益。

**为什么不直接用大模型API？**

当前任务是固定标签分类，轻量本地模型能展示训练、评估和部署基础，也不依赖付费API。没有做API模型对比，因此不能断言它一定更便宜或更好。

**支持中文和未知意图吗？**

没有验证。未来要用合法的中文标注数据和独立域外测试集来评估。输入保护和低置信度分流不能替代这些验证。

**这是否有实际生产效果？**

目前只有公开历史数据上的离线效果和本机演示。没有真实业务接入、A/B实验、人工成本测量、稳定性或并发容量测试。下一步要先定义业务指标并收集有授权的数据。

## 自己真正做一次改进

选一个小任务，保留修改前后的Git差异和验证记录：

- 在网页额外显示第一名和第二名的概率差，只把它作为描述信息，不改变已有阈值。
- 增加命令行批量输入文件，检查每行错误和空行处理。
- 在错误分析中，按句长区间描述错误率，并明确这是事后描述，不拿test选参数。

不建议第一天就同时增加RAG、向量数据库、LoRA和多Agent；先把这个单任务讲透，再根据实际岗位选择扩展。
